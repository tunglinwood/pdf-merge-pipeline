## 6. 已知限制

1. **回复里会出现重复内容与一行开场白**：FastGPT 会把 agent 的执行文本与「指定回复」节点的文案都放进同一条回复，
   且 agent 在调用工具前先输出了 `I'll start by reading the skill documentation.`。这是平台/模型行为，不是本工作流的配置问题；
   交付的页数、尺寸与链接本身不受影响。B 线的验收项（AC-B1~AC-B6）不涉及回复去重（回复去重是 A 线 FR-A12 的范围）。
2. **沙箱镜像默认不带 LibreOffice**：docx/xlsx/pptx 转换依赖沙箱内安装 LibreOffice。本轮实测中沙箱已具备该依赖
   （首次运行含安装，耗时较长：用例 1 用时 270 秒，用例 2/3 分别为 97 / 168 秒）。若某次沙箱缺 LibreOffice，
   对应文件会按「转换失败并说明原因」处理，其余文件照常合并（SKILL.md 里已写明安装与兜底步骤）。
3. **文档类排版与 Office 原生渲染可能有细微差异**：验收口径为纸张尺寸与方向一致，不要求像素级排版一致。

## 7. v1.2 轮次：同名不同后缀覆盖缺陷与修复（TEAM-85）

### 7.1 缺陷

v1.1 轮次交付后复盘发现：转换步骤把每个文件的中间产物统一写成 `<stem>.pdf`，
**同 stem 不同后缀**的文件（`同名素材.png` / `同名素材.pdf` / `同名素材.docx`）会写进同一个 `同名素材.pdf`，后者覆盖前者。

合并时每个条目都指向同一路径，最终产物的页序与页面尺寸，与「每个文件各自转出来的那一份」不一致。
更隐蔽的是：报告里 `files[].page_sizes_pt` 记的是各自转换时的尺寸，`merged_page_sizes` 记的是合并产物的尺寸，
两边各自自洽，`page_sizes_match`（产物 vs 报告）因此通过——它比的是同一份错误结果的自洽性，不是「产物是否等于各文件拼接」。

### 7.2 改动（技能包 v1.2）

| 项 | 改前 | 改后 |
| --- | --- | --- |
| 单文件中间产物命名 | `<stem>.pdf`（同 stem 互相覆盖） | `<序号>_<stem>.pdf`（`01_a.pdf` / `02_a.pdf` / `03_a.pdf`），同 stem 不再互相覆盖 |
| Office 转换产物 | LibreOffice 按源文件名输出 `<stem>.pdf` | 转换前先删同名旧产物（拒绝上一轮的残留文件），转换后改名成带序号的产物名 |
| 页序一致性校验 | 无 | `verify_result.py` 新增 `page_order_matches_files`：断言合并结果等于各文件 `page_sizes_pt` 按上传顺序的拼接，并与总页数交叉验证 |
| 下载链接字节数校验 | 只看魔数（`%PDF-`） | `download_link_openable` 同时要求魔数与字节数一致（截断/陈旧文件不再算通过） |
| 样例文件生成 | `tools/make_samples.py` 的 PNG 扫描线按像素换行，生成的是结构非法的 PNG（PIL 报 `unrecognized data stream contents`） | 按「每行 1 过滤字节 + width×3 字节 RGB」逐行生成，PIL 可正常读取 |
| 实测工具的依赖路径 | 写死 `/home/huasmex/workspace/fastgpt-mcp` | 改为环境变量 `FASTGPT_MCP_DIR` / `FASTGPT_MCP_ENV` / `FASTGPT_MCP_CONFIG`，默认按标准安装位置推断 |
| 回归测试 | 「各文件拼接 vs 合并产物」自洽式断言（文件转换失败时也会假通过） | `tests/test_stem_collision.py` 断言独立算出的期望值（600×900 / 400×600 / 595.28×841.89 / 841.89×595.28，4 页）且**不允许任何文件转换失败** |
